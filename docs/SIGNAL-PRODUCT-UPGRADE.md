# SIGNAL 제품 방향과 개선 기준

## 결론

SIGNAL의 우선 과제는 데이터 소스나 메뉴를 늘리는 것이 아니다. 이미 있는 뉴스 요약, 시장 브리핑, 관심종목, 공시와 일정을 **이해 → 나와의 관련성 → 원문 확인**으로 연결하는 것이다.

제품 방향: **시장의 맥락을 짧게 이해하고 관심기업의 변화를 확인하는 브리핑 앱**.

실시간 시세 서비스와 속도 경쟁을 하거나 검증되지 않은 투자 점수를 만드는 대신, 발행 시각과 출처를 명확하게 보여주고 읽기 비용을 줄인다. 뉴스/시장/시세/공시는 각자의 탐색 화면을 유지하고, 홈은 이들의 복제 목록이 아니라 읽기 시작점으로 사용한다.

## 외부 서비스 비교

공식 공개 웹 화면과 제품 소개를 기준으로 비교했다. 로그인 후 기능, 유료 기능의 품질, 실제 앱의 지연시간은 직접 측정하지 않았다.

| 서비스 | 확인한 구성 | SIGNAL에 적용할 원칙 |
|---|---|---|
| SAVE | 시장/관심/캘린더/스크랩 진입, 오늘 주요뉴스와 최신순 뉴스, 출처 탐색 | 전체 시장에서 내 관심으로 빠르게 좁히고, 읽기와 출처 확인을 같은 흐름으로 둔다 |
| StockNow | 관심종목, 공시, 실적 일정, 컨퍼런스콜을 연결한 기업 리서치 흐름. 데스크톱은 시장/섹터/일정을 함께 배치 | 기능별 메뉴를 늘리는 대신 관심기업을 중심으로 정보를 연결한다. 넓은 화면은 읽는 영역과 참고 영역을 분리한다 |

출처: [SAVE 뉴스 화면](https://www.saveticker.com/news), [StockNow 공식 제품 소개](https://stocknow.ai/en).

StockNow의 실시간 컨퍼런스콜·검색·가격 제공은 공식 소개상 기능이다. SIGNAL에 같은 기능을 무료 데이터만으로 구현할 수 있다는 뜻은 아니다. 공개 화면의 구조로부터 도출한 위 원칙은 SIGNAL에 대한 설계 판단이다.

## 프로젝트 진단

| 문제 | 코드에서 확인한 상태 | 영향 |
|---|---|---|
| 우선순위가 약함 | 홈에서 키워드가 브리핑 본문보다 먼저 노출되고 주요 뉴스는 대부분 제목만 사용 | 정보는 많아도 무엇을 읽어야 하는지 판단하기 어렵다 |
| 개인적 관련성이 약함 | 관심종목은 시세에 쓰이지만 홈의 뉴스 목록은 전체 최신 목록만 제공 | 등록한 관심종목이 읽기 경험에 충분히 반영되지 않는다 |
| 출처 식별 비용 | 홈 뉴스는 작은 출처 아이콘과 일부 토픽 위주 | 원문이 어디에서 왔는지 한눈에 알기 어렵다 |
| 방문 간 연속성 | 개별 이슈를 읽었는지 표시하지 않음 | 같은 항목을 반복해서 확인하게 된다 |
| 초기 표시 지연 | `HomeFocusContent`가 여러 API의 `Promise.all` 완료 후 전체 상태 갱신 | 가장 느린 보조 API가 뉴스와 브리핑 표시까지 지연시킨다 |
| 실패와 빈 데이터 혼동 | 여러 호출에서 오류를 `[]` 또는 `null`로 변환 | 장애가 소식 없음처럼 보이고 새로고침 시 기존 정보가 사라진다 |
| 공통 요청의 오류 전파 | HTTP GET 중복 제거의 `void run.finally()`에서 별도의 rejected promise 발생 | 원래 요청을 처리해도 미처리 오류가 추가 발생. 브라우저 오류 화면이 복구 동작을 방해할 수 있다 |
| 화면 폭 활용 | 모바일과 넓은 화면 모두 긴 단일 순서에 가까움 | 넓은 화면에서는 읽는 행이 길고 참고 정보가 멀다 |

분석은 홈·다이제스트 상세·시세 및 일정 연동·공용 레이아웃과 API 캐시를 중심으로 수행했다. 모든 서버 쿼리와 네이티브 기능에 대한 종합 감사는 이번 범위가 아니다.

## 반영한 구조

### 홈

1. 브리핑: 헤드라인 → 짧은 요약 → 전문 이동 → 관련 키워드. 배경 카드로 다시 감싸지 않고 섹션 선과 타이포로 구분한다.
2. 뉴스: 제목 앞 시장 분류, 관련 관심종목, 제목, 요약 2줄, 출처명·아이콘, 생성 시각. 상세에서 전체 요약과 원문을 확인한다.
3. 일정·바로가기: 읽기의 보조 영역. 휴일·정책 일정·주요 지표·관심종목 실적의 기존 선별 규칙은 유지한다.
4. 시세: 현재 가격 성격을 유지하며 오늘 날짜에서만 표시한다. 지연/종가와 사용자 등락색 설정을 유지한다.
5. 섹터: 기존 신선도 조건을 충족할 때만 표시한다.

아이폰은 위 순서의 세로 화면이다. iPad/웹은 **콘텐츠 pane 폭 960px 이상**에서 뉴스와 일정·바로가기를 나란히 배치한다. 좁은 iPad 분할 화면에서는 세로로 돌아온다. 사이드바·공통 헤더·뒤로가기 구조는 유지한다.

### 뉴스 읽기

- 홈 뉴스는 `관심 소식 / 전체 / 저장`으로 나누고 관심 소식을 기본으로 연다. 관심 소식은 아래 10개 대상에 대해 선택일 포함 최근 7일의 이슈를 서버 `symbols` 필터로 조회한다. 전체는 선택일 기존 카테고리 목록, 저장은 날짜와 무관한 이 기기의 개정 스냅샷이다.
- 대상은 `domain/home/focusUniverse.ts`가 기준: 삼성전자, SK하이닉스, NVIDIA, Apple, Google, Tesla, SpaceX, SPY, QQQ, Bitmine. 전체 10개 또는 하나를 선택한다. 시세 관심목록은 독립적으로 유지하며 강제로 교체하지 않는다.
- Google은 GOOG/GOOGL을 함께 조회하고 국내 코드는 별칭을 정규화한다. 관련 기업명은 표시하되 제목 문자열로 종목 연관성을 추측하지 않는다. 서버 `symbols` 태그가 없는 기존 이슈는 자동 편입하지 않는다.
- 관심 소식은 최대 100개 조회 후 표시 개수만큼 보여주고 더보기로 펼친다. 오래된 소식을 새 소식으로 가장하지 않고 발행 시각·추가/정정·읽음을 유지한다. 요약이 없는 대상의 내용을 임의로 만들지 않는다.
- 식별자 확인(2026-09-22): [SpaceX 공식 IR](https://ir.spacex.com/updates/releases-details/2026/Space-Exploration-Technologies-Corp--Announces-Closing-of-Initial-Public-Offering-Including-Full-Exercise-of-Underwriters-Option-to-Purchase-Additional-Shares-2026-RgoR-Y1Vwh/default.aspx)의 SPCX, [Bitmine 공식 사이트](https://www.bitminetech.io/)의 BMNR. 상장 상태·티커 변경 시 카탈로그를 갱신한다.
- 글로벌/국내/크립토의 최신 배치를 각각 최대 12건 조회한 뒤 합친다. 관심종목 필터를 먼저 적용하고 설정의 표시 개수를 적용한다.
- `symbols`의 정확한 일치만 사용한다. 한국 종목의 숫자코드·`.KS`/`.KQ`·`KRX:`는 같은 식별자로 취급한다. 제목 문자열로 관계를 추측하지 않는다.
- 최신순은 UTC 시각 비교다. 같은 시각은 ID로 안정적으로 정렬하고 중복 ID를 제외한다.
- 상세를 성공적으로 열면 해당 언어·이슈 개정판에 읽음 표시를 남긴다. 목록 조회만으로 읽음 처리하지 않는다.
- 읽음은 기기 로컬에 최대 300건 보관한다. 계정/기기간 동기화, 추천 순위 변경에는 사용하지 않는다.
- v3는 `storyId`와 `revisionId`로 읽음 상태를 구분한다. 새 개정만 다시 미열람이 된다. 기존 v2는 내용/시각 해시를 사용한다. `최신` 표시는 기존 1시간 신선도 규칙에 해당하면서 아직 읽지 않은 항목에만 표시한다.
- 관심종목을 저장하면 홈의 관련 이슈와 시세도 현재 목록으로 갱신한다.

### 로딩과 오류

- 브리핑·각 뉴스 카테고리·시세·코인·일정·섹터 응답을 따로 반영한다. 보조 API가 느려도 뉴스부터 읽을 수 있다.
- 동일 날짜/언어의 새로고침 실패 시 직전 성공 데이터를 유지하고 실패 영역을 알린다. 재시도 버튼은 기존 새로고침 경로를 사용한다.
- 날짜/언어가 변경되면 다른 범위의 데이터를 비운다. 이전 요청이 나중에 끝나도 현재 화면을 덮어쓰지 않는다.
- 기본 API 캐시와 PTR의 `bypass` 규칙은 유지한다. 관심종목 필터는 별도 캐시 키로 조회하며 읽음/저장 표시용 폴링은 없다.
- 오류를 빈 데이터로 취급해 한국어 폴백을 호출하지 않는다. 번역 브리핑이 정상 응답에서 실제로 없을 때만 기존 한국어 폴백을 사용한다.
- 공통 HTTP 요청 정리는 성공/실패 양쪽을 소비한다. 중복 요청 공유는 인증 없는 GET이면서 URL·시간제한·재시도 조건까지 같은 요청만 대상으로 한다. 서로 다른 로그인 상태의 응답을 공유하지 않는다.

## 이슈·기업 연결

- 대표 뉴스 한 건은 더 큰 제목과 최대 3줄 요약으로 먼저 보여준다. 나머지는 간결한 목록을 유지한다.
- 상세는 추가/정정 사실 → 근거 원문 → 맥락 → 이전 개정으로 연결한다. 저장 버튼은 이 기기에 최대 100개를 보관하며 계정 동기화는 하지 않는다.
- 종목 상세의 기업 타임라인은 관련 뉴스 이슈·공시·시장 브리핑을 시간순으로 연결한다. 이슈 근거로 사용된 원문은 중복 노출하지 않는다. 예정 실적은 별도로 표시한다.
- Codex 생성기는 기존 사건과 비교해 새 사실이 있을 때만 개정을 만든다. 새 개정 ID를 기존 알림 인박스에 연결하며 개별 사용자 사건 구독은 아직 아니다.

## 다음 우선순위

| 순위 | 작업 | 완료 판단 기준 |
|---|---|---|
| 1 | 생성 품질 운영 검수 | v3 운영 배포 후 신규성·정정·독립 출처·사건 연결을 표본 확인 |
| 2 | 관심종목 그룹·사건 구독 | 계정 기반 그룹과 개별 사건 후속 알림, 해제·탈퇴 처리까지 정의 |
| 3 | 기기간 읽음/저장 동기화 | 동의된 계정 데이터로 동기화, 로그아웃·탈퇴 처리 및 데이터 삭제 제공 |
| 4 | 품질과 체감속도 측정 | 첫 유효 콘텐츠 표시 시간, 부분 실패율, 원문 연결 유효성, 중복 이슈율을 수집. 수집 목적·보존기간·개인정보 범위를 먼저 확정 |

이슈 품질은 UI만으로 해결되지 않는다. 다음 단계에서는 검증용 뉴스 묶음을 정하고 중복·독립 출처·실제 새 사실을 사람이 검토한 뒤 자동화 규칙을 변경한다. 새 점수나 AI 긍정/부정 배지를 먼저 만들지 않는다.

## 검증 범위

- `npm run verify`: 타입 검사와 도메인 테스트. `npm --prefix server run test:news-revisions`: PostgreSQL(PGlite)에서 V21·개정 적재·재전송·충돌·근거 검증·조회 테스트.
- 웹 브라우저: 390px 라이트/다크, 1194px 태블릿, 1440px 데스크톱, 320px 최대 글자 크기+볼드의 5조건에서 가로 넘침·필터·상세 복귀·읽음·새로고침 실패 복구·날짜 변경 후 빈 결과 확인. 시세 응답을 3.5초 지연시켜도 뉴스가 먼저 표시됨을 확인했다.
- 브라우저 상호작용은 테스트 API 응답을 사용한다. 현재 로컬 설정의 API 주소는 브라우저에서 네트워크 오류, 상태 URL에서 Railway fallback 404가 확인되어 실데이터 내용과 운영 서버 지연시간은 검증하지 않았다. 이것만으로 다른 환경의 운영 API 상태를 단정하지 않는다.
- iOS production JavaScript/Hermes 번들 export 통과. 네이티브 SDK 변경이나 실제 기기 빌드를 의미하지 않는다.
- 실제 iPhone/iPad 설치·네이티브 PTR 제스처·OTA 배포는 별도 확인 대상이다. V21은 작성/테스트만 했으며 운영 DB에 적용하지 않았다. 위 브라우저 검증은 초기 홈 개편 기준이고 개정 이력/저장/기업 타임라인의 실제 기기 검증을 의미하지 않는다.
